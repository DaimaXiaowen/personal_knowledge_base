# Git 分支与合并

## 来源

- 《Pro Git（第 2 版）》第 3 章「Git 分支」：https://git-scm.com/book/zh/v2
- 动手练习：learngitbranching.js.org 的分支关卡

## 核心内容

### 分支的本质：只是一个指针

分支 = 指向某次提交的可移动指针（实现上是一个 40 字符哈希的小文件），创建分支几乎零成本；`HEAD` 是指向「当前所在分支」的指针，切换分支就是移动 HEAD。

这也解释了 [[01-Git 基础概念|基础概念]] 里的疑问：每个提交对象都记录父提交哈希，形成一条链，所以改写任何一个历史提交，它之后所有提交的哈希都会变——父指针变了，整条后链全部重算。

### 基本操作

- `git branch <name>`：创建分支；`git branch`：列出；`git branch -d <name>`：删除（未合并会拒绝，`-D` 强删）
- `git switch <name>`：切换分支；`git switch -c <name>`：创建并切换（新命令，取代了 `checkout` 的分支职能）
- `git log --oneline --graph --all`：查看全部分支的拓扑图

### 合并的两种情形

- **Fast-forward**：目标分支是当前分支的直接后代 → 指针直接前移，不产生新提交
- **三方合并**：两条分支分叉了 → Git 找到共同祖先，做三方合并，生成一个有两个父提交的新合并提交

### 冲突处理

两边改了同一文件的同一区域时，合并会停下来，文件里出现 `<<<<<<<` / `=======` / `>>>>>>>` 标记。处理四步：

1. 打开冲突文件，在标记之间手工取舍内容，删掉标记行
2. `git add <file>` 标记冲突已解决
3. `git commit` 完成这次合并
4. 不想合了就 `git merge --abort`，回到合并前的状态

减少冲突的习惯：小步提交、改动前先拉最新代码、一个分支聚焦一件事。

### rebase 与 merge 的取舍

- **merge**：完整保留「分叉与合并」的真实历史，不线性但诚实
- **rebase**：把当前分支的提交摘下来，在目标分支末尾重新播放一遍，历史变成一条直线，干净易读；代价是**改写了历史**（所有重放提交的哈希都变）

**黄金法则：已推送到共享分支的提交不要 rebase（同理不要 reset）。** 这回答了 [[02-Git 常用命令|常用命令]] 里的疑问——`reset --hard` / rebase 都是改写本地历史，一旦推送，协作者本地还留着旧提交，拉取时会出现两条「内容相似、哈希不同」的平行历史，几乎必然搞乱。未推送的本地提交、个人分支同步主干，用 rebase 很合适。

### stash：临时藏起做到一半的改动

- `git stash`：把工作区和暂存区的改动收起来，工作区恢复干净
- `git stash list` 查看；`git stash pop` 取出并删除记录；`git stash apply` 取出但保留记录
- 典型场景：正在写 A 功能，线上突然要修 bug，先 stash 再切分支
